  keeps two parallel tickets from editing the generated files at once.

## 5. Backend

### 5.1 Layering

The template's layering holds: routers → controllers → services → repositories, with DTOs
separate from database models.

- **Routers** parse HTTP and translate responses. No rules, no queries.
- **Controllers** map DTOs to service calls and back.
- **Services** own use cases, authorization, transactions and calls into the domain.
- **Domain** is pure: explicit inputs, returned results, no I/O. It imports nothing from the
  other layers.
- **Repositories** own queries.
- A test asserts that `domain/` imports no other application package, SQLAlchemy, FastAPI or
  the settings module.

Effects are passed in. `clock.py` defines `Clock` with `now() -> datetime` in UTC; services
receive it, and tests pass a fixed one. `wiring.py` is the one place that builds services from
settings.

### 5.2 Data model

Every table has a UUID primary key unless noted, and every timestamp is `timestamptz`.

| Table | Holds | Notes |
| --- | --- | --- |
| `users` | Identity subject, email, display name, pursuer, profile handle and `public`, reminder preferences, `chase_changed_at`, `reminders_planned_at` | The handle is unique when set. |
| `day_settings` | `user_id`, `effective_from` (a date), time zone, day start, day end | Append-only. The row with the latest `effective_from` on or before a date applies to that date. |
| `habits` | Name, unit, chunk, position, `effective_from`, `archived_from` | A habit belongs to a date when `effective_from <= date < archived_from`. |
| `habit_targets` | `habit_id`, `effective_from`, target | Append-only, so a settled day's shares can always be recomputed. |
| `days` | `user_id`, date, `starts_at`, `ends_at`, `starting_lead`, and once settled: `result`, `end_lead`, `caught_at`, `streak_after`, `settled_at` | Unique on (`user_id`, date). The window is stored when the day is created, so later setting changes cannot move it. |
| `logs` | The client's ID as primary key, `user_id`, `habit_id`, amount, `logged_at`, `received_at`, source, day date, `undone_at` | An undone log stays as a tombstone. |
| `sessions` | `user_id`, token digest, device name, `created_at`, `last_used_at`, `expires_at` | |
| `keys` | `user_id`, kind (`api` or `mcp`), name, digest, `created_at`, `last_used_at`, `revoked_at` | |
| `installations` | `user_id`, installation ID, APNs token, widget push token, environment, app version | Unique on (`user_id`, installation ID). |
| `push_jobs` | `user_id`, day date, kind, `due_at`, payload, `sent_at`, attempts | Unique on (`user_id`, day date, kind), so a reminder is sent once. |
| `push_deliveries` | What the recording sender "sent" | Development and tests only. |

T04 creates every table in one initial migration, so that feature tickets do not add
migrations in parallel. A ticket that needs a schema change adds one migration and lands it
first, like a contract change.

Only settled results are stored. A running day's state is always computed from its logs
(constitution §4).

### 5.3 The rules

These live in `backend/src/feed_the_goose/domain/`. Every number is a server setting with the
default shown.

**The day window.** `domain/day.py` turns a date and a `day_settings` row into `starts_at` and
`ends_at`.

- `starts_at` is `day_start` on the date in the time zone. `ends_at` is the next `day_end`
  after it, which may be on the following date.
- The nominal length, by local clock time, must be 8 to 22 hours.
- The pursuer walks evenly between the two instants. Its pace is `100 / hours`, where the
  hours are the real time between `starts_at` and `ends_at`, so a day across a clock change
  still totals 100 steps.
- A day is followed by the day with the next date. That day's window comes from the settings
  effective on its date, and it never starts before the previous day ends.
- **The first day.** A user's first day starts when the first habit is created, if that is
  later than the day's start. The pace is unchanged, so the pursuer walks fewer than 100 steps
  that day.
- A date with no habit has no day and no chase. The streak and the carried lead pass over it.

**The chase.** `domain/chase.py` takes the window, the starting lead, the day's habits with
their targets, the day's logs that are not undone, and an instant `at`. It returns the state.

- `walked(t) = pace × hours since starts_at`, capped at `ends_at`.
- Each habit's share is `100 / number of habits`. A log earns `share × amount / target`, capped
  at what is left of that habit's share.
- Logs are applied in order of `logged_at`, then of ID.
- `lead(t) = starting_lead + earned(t) − walked(t)`.
- **Caught:** the first instant at which the lead is 0 or less. Logs at that instant are
  applied first. A lead of exactly 0 at `ends_at` is caught. Logs after the catch earn nothing.
- **Complete:** the instant the last habit reaches its target while the day is not caught. The
  lead freezes at that instant. Later logs earn nothing.
- **Short:** `at` is at or after `ends_at`, and the day is neither complete nor caught.
- **Running:** otherwise.
- **Night logs.** A log between `ends_at` and the next day's start belongs to the day that
  ended. The pursuer is not walking, so it can raise the lead or complete the day. It cannot
  undo a catch that happened before it.
- `caught_at`, for a running day, is when the lead would reach 0 with no more logs, or null
  when that is after `ends_at`.
- Arithmetic is exact (`Fraction` or `Decimal`). Rounding happens only when a DTO is built:
  steps to one decimal place, `steps_per_hour` to two.

**The next day's starting lead.** 100 after a complete day, 100 after a caught day, and the
lead at settlement after a short day. A user's first day starts at 100.

**The streak.** `domain/streak.py`. A complete day adds one, a short day leaves it, a caught
day sets it to 0. The stage is 0, 1, 2, 3 or 4 for streaks from 0, 3, 7, 14 and 30. The Chase
reports the streak including today when today is complete.

**The example table.** T03 implements these as a parametrized test, with expected values
worked out by hand, not taken from the code. The base day is 2026-11-26 in
`America/New_York`, 06:00 to 00:00 (11:00Z to 05:00Z, 18 hours, pace 5.56), a starting lead of

### 5.4 Days and settlement

`services/days.py` owns `ensure_days(user, now)`, which every chase read and write calls first,
inside one transaction that locks the user's row.

1. Create the day rows that should exist up to `now`, in date order.
2. For each day whose successor has started and that is not settled: compute its final state
   from its logs, store `result`, `end_lead`, `caught_at` and `streak_after`, and set
   `settled_at`.
3. Return the current day: the latest one whose `starts_at` is at or before `now`.

There is no scheduled job for settlement. A user who was away has their missed days settled in
order on their next request. A profile read does the same, so a public page is never behind.

During the night the current day is the one that just ended. Its state is computed, not
stored, until the next day starts.

### 5.5 Logs

- `POST /v1/logs` inserts with `ON CONFLICT (id) DO NOTHING`.
  - A new ID returns 201.
  - An ID this user already has returns 200 with the stored log, its recomputed event and the
    current chase. The request's other fields are ignored.
  - An ID another user has returns 422 `invalid`.
- The server accepts a log when `logged_at` is no later than its arrival plus 2 minutes, and
  its day has not settled. Otherwise it answers 422 `invalid` or 409 `day_settled`.
- The day a log belongs to comes from `logged_at`, not from its arrival.
- `DELETE /v1/logs/{id}` sets `undone_at`. Undoing twice returns the same result. A later
  `POST` with that ID returns the log, still undone.
- **The event** is a function of the stored logs, so it is the same on a replay:
  - `complete` when this log is the one at which the last habit reached its target;
  - `caught` when the log's `logged_at` is at or after the catch;
  - `gain` otherwise, with the steps it earned, which may be 0.
- Each write that can change a chase sets `users.chase_changed_at` in the same transaction.

### 5.6 Identity and credentials

- `identity/` defines `IdentityVerifier`: a token goes in, and a verified subject, email and
  `email_verified` come out.
  - `Auth0Verifier` checks issuer, audience, expiry and signature against the tenant's keys,
    with `joserfc`. Tests run it against a fake issuer that serves its own keys.
  - `DevVerifier` accepts tokens signed by the server's own dev key. `POST /dev/token` issues
    them for an email.
- `POST /v1/auth/session` verifies the token, checks the email against `ALLOWED_EMAILS`
  (403 `identity_not_admitted` otherwise), creates the user on first sign-in, and returns a
  session token. Only its SHA-256 digest is stored.
- **Development guard.** The dev verifier and the `/dev` routes exist only when
  `ENV` is `development` or `test`. With `ENV=production` the app refuses to start if either is
  enabled. A test covers the refusal.
- One dependency resolves the `Authorization` header to a principal with its credential kind.
  Each router declares the kinds it accepts (the spec's Credentials table). The wrong kind is
  401 `unauthenticated`.
- Keys are `ftg_` plus 32 random bytes, URL-safe. They are shown once and stored as digests.
- Account deletion removes every row for the user. Deleting the identity at the provider goes
  through an `IdentityAdmin` protocol whose only implementation for now does nothing.

### 5.7 MCP

Follows Slate's `mcp_server.py`.

- FastMCP serves Streamable HTTP at `/mcp`, stateless, with JSON responses:
  `http_app(path="/mcp", stateless_http=True, json_response=True)`.
- It is mounted as ASGI middleware ahead of routing, and its responses are `no-store`.
- A `TokenVerifier` accepts MCP keys only.
- `services/tools.py` holds the tool catalog: `get_chase`, `list_habits`, `get_history`,
  `log_habit`, `undo_log`. Each calls the same service as its REST route, so the rules run in
  one place. A future in-app assistant uses the same catalog.
- Habit names in results are wrapped as `{"untrusted": "..."}`. Error messages are fixed text.
- `log_habit` takes an `idempotency_key`, which becomes the log's ID, and sets `logged_at` to
  the server's time.

### 5.8 The public profile

- `GET /v1/profiles/{handle}` returns JSON. `GET /{handle}` returns the same as an HTML page.
- Both are built from one function that reads an explicit projection: display name, pursuer,
  streak, stage, state, lead, `as_of`, `steps_per_hour`, `caught_at`, and the last 35 days'
  results. **[Amended]** `caught_at` replaced `day_ends_at`, which would publish the day's end
  (constitution §5). The page's sky follows the day's state, not the clock, for the same reason.
  A test asserts that the JSON has exactly those keys and that the page contains no habit name
  from the seed.
- Both re-check `public` on every request, return 404 when it is off, set no cookie, read no
  credential, and send `Cache-Control: no-store`.
- The page is one self-contained HTML document: inline CSS, an inline SVG scene taken from
  prototype `04-app-screens`, and the 35-day grid. It is built with `string.Template` and
  `html.escape`. The display name is the only user text on it and is escaped.
- `/{handle}` is registered last. Handles that would shadow a route are refused when set:
  `v1`, `mcp`, `dev`, `healthz`, `readyz`, `docs`, `openapi.json`, `static`, `favicon.ico`,
  `robots.txt`, `.well-known`.
- The goose words on the page belong to the pursuer's template, `profile/goose.html`, not to
  the service (constitution §2).

### 5.9 Reminders and the worker

- `push/planner.py` is pure. Given a chase and the user's preferences it returns at most three
  reminders with their due times:
  - when the lead falls below `when_lead_below` (default 30);
  - an hour before `caught_at`;
  - an hour before `day_ends_at` if the day is not complete.
  A reminder that falls in quiet hours, or in the past, is dropped.
- `worker.py` is a loop, run as `python -m feed_the_goose.worker`.
  1. For each user whose `chase_changed_at` is later than `reminders_planned_at`, or whose
     current day is new: replace that day's unsent `push_jobs` with the planner's output.
  2. Send each job that is due, to each of the user's installations, through a `PushSender`.
     Mark it sent. Rows are claimed with `FOR UPDATE SKIP LOCKED`.
- `PushSender` has two implementations.
  - `ApnsSender`: HTTP/2 through `httpx[http2]`, with an ES256 token signed by `joserfc`. A
    `410 Unregistered` deletes the installation's token. Tests run it against a fake APNs
    server.
  - `RecordingSender`: writes to `push_deliveries`. It is used when no APNs key is set.
    `GET /dev/pushes` lists what it recorded.
- Widget refresh by push is not built yet (§0.2). `installations` keeps the
  `widget_push_token` so that it can be added without a schema change.

### 6.3 The rig and the clips

Ported from `spikes/swiftui-goose/`, which ported `docs/prototypes/src/rig.js` and
`05-animations`. The spike found the risk low: Snap, Feast and Peck matched the prototype's
frames at 60 fps in the simulator. It was never run on a device or at 120 Hz.

- A clip is a pure function from seconds to a `Pose`. `TimelineView(.animation)` drives it,
  and one `Canvas` draws the scene in the prototype's 340 by 176 units.
- `SceneCanvas` takes a pose and a layout. The layout is width-flexible: the spike's fixed
  frame letterboxed or cropped in a widget, so the ground, the dashes and the sky extend to
  fill any aspect.
- `Canvas` does not clip to its bounds. Clip explicitly.
- The scene takes the chase's inputs as plain values: the lead as a fraction, the sky's time
  of day, the stage's size (0.5, 0.75, 1, 1.3, 1.7), and whether the goose is a gosling.
- With Reduce Motion on, a clip shows its last frame.
- Known spike defects to fix in the port: one Feast frame at 2.40 s has no crumbs, and
  Shrikhand sits taller in SwiftUI `Text` than in the prototype.
- If the final art needs mesh deformation or an artist's timeline, Rive replaces `Canvas`
  later. Clips stay functions of time so that the move is cheap.

### 6.4 App architecture

Plain SwiftUI. One `@Observable` model per screen, exposing one state enum that the view
switches over. No Composable Architecture and no dependency-injection framework.

- `App/LiveEnvironment.swift` builds an `AppEnvironment` of live services once. Each feature's
  entry view takes it in its initializer.
- In debug builds the `-FTGUseFixtures` launch argument swaps in `AppEnvironment.fake`, built
  from the fixtures, for the app, the widgets and the intents. Feature tickets record their
  proof this way before the backend's routes exist.
- `SessionModel` holds signed-out, signed-in-without-habits, or signed-in. `RootView` switches
  on it between `SignInView`, `HabitSetupView` and the tabs for Today and Settings.
- **Sign-in seam.** `IdentityProvider` is a protocol that returns an identity token.
  `DevIdentityProvider` calls `POST /dev/token` and is compiled only in debug builds. The
  Auth0 provider (AppAuth-iOS, PKCE, an ephemeral browser session) is added later behind the
  same protocol. The session exchange with `POST /v1/auth/session` is shared.
- T11 creates a placeholder view for each feature, so `RootView` compiles from the start and
  each feature ticket replaces its own placeholder without touching the root.

| `App/Features/SignIn/` | Sign-in, the allowlist refusal | T14 |
| `App/Features/Habits/` | First-run habit setup; add, edit, reorder, archive | T15 |

### 6.5 Showing a chase

- **`ChaseClock`** does the only chase arithmetic on the phone. It keeps the device time at
  which a chase was received next to it, and treats the difference from `as_of` as the clock
  offset. For a running day, the lead shown is
  `lead − steps_per_hour × hours since receipt`, never below 0, and it stops at `day_ends_at`.
  A wrong device clock therefore cannot distort the chase.
- **`ChaseStore`** is the one place a new chase enters the app, the extension or an intent. It
  writes the chase and its receipt time to the App Group, reloads the widget timelines, and
  decides which clip, if any, the change deserves:
  - an event from the user's own log: `gain` plays Snap, `complete` plays Feast, `caught`
    plays Peck;
  - a refresh in which the state went from running to complete plays Feast, and from running
    to caught plays Peck;
  - Feast and Peck play once per day per device. The last one played is kept in the App Group.
- **Refreshing.** Today fetches the chase when it appears, when the app becomes active, on
  pull to refresh, every 60 seconds while visible, and at `caught_at`, `day_ends_at` and
  `next_day_starts_at`. The app shows a day as caught or complete only when the server says so.
- When a fetch fails, the last chase stays on screen, marked as out of date with its age.

### 6.6 The retry queue

`LogQueue` in `GooseCore`, used by the app, the extension and the intents.

- A queued log is one file in the App Group's `queue/` directory, named by its ID and written
  atomically. Removing a log is deleting its file. Three processes can therefore use the queue
  without a shared lock, and sending a log twice is harmless because the server ignores a
  repeated ID.
- To log: create the ID (UUIDv7) and `logged_at`, write the file, then send `POST /v1/logs`
  with a 5-second timeout.
  - Success: hand the chase and event to `ChaseStore` and delete the file.
  - 409 `day_settled`: delete the file and tell the user the log was too late.
  - 404 or 422: delete the file and report the error. Retrying cannot help.
  - Anything else: keep the file and say the log will count when the phone is back online.
- The queue drains when the app becomes active, when the network path becomes satisfied, and
  from a background task. It sends in `logged_at` order.
- Today lists what is queued, so a waiting log is never shown as counted.

### 6.7 Widgets

Both widgets read the cached chase and habits from the App Group and draw with `GooseRig`.
Neither can play a clip, so each shows one static pose.

- **Chase** (status): `systemSmall`, `systemMedium`, `accessoryRectangular`,
  `accessoryCircular`. It shows the scene, the lead, and the stage.
  - Its timeline holds an entry every 15 minutes, computed with `ChaseClock`, up to the
    earliest of `caught_at`, `day_ends_at` and `next_day_starts_at`. At that time it asks for
    a new timeline, which fetches the chase.
  - At `caught_at` it shows a lead of 0. It says "caught" only after the server does.
- **Feed** (logging): `systemMedium` with up to three buttons, `systemSmall` with one. Each is
  a `Button(intent:)` for one chunk of an unfinished habit, such as "+10 pushups". On a
  complete or caught day it shows the result instead.
- Signed out, or with no cached chase, both show "Open Feed the Goose".
- A chase older than its next expected refresh is drawn with its age.

### 6.8 App Intents

In `Intents/`, compiled into the app and the extension.

| Intent | Parameters | Result |
| --- | --- | --- |
| `LogHabitIntent` | A habit; an optional amount, defaulting to the chunk | A sentence with what was logged and the new lead, or the queued notice |
| `UndoLastLogIntent` | None | A sentence with the new lead |
| `GetChaseIntent` | None | The state and the lead |

- `HabitEntity` is an `AppEntity` whose query reads the cached habits.
- Every intent goes through `LogQueue` and `ChaseStore`, so a widget tap and an in-app tap
  behave the same. The log's `source` is `widget` from a widget button and `shortcuts`
  otherwise.
- There is no `AppShortcutsProvider`, because v1 has no Siri phrases. The actions still appear
  in the Shortcuts app.

### 6.9 Push registration

When reminders are turned on, the app asks for notification permission, registers for remote
notifications, and sends the token with `PUT /v1/me/devices/{installation_id}`. The
installation ID is a UUID kept in the App Group. Sign-out deletes the registration.

Whether the simulator issues a device token without a signing team is not known. T17 checks.
If it does not, the registration code is covered by unit tests with a fake registrar, and the
report says delivery is unverified.

### 8.3 Capture

The spike's commands work. `$UDID` is the pinned simulator.

```sh
xcrun simctl boot $UDID 2>/dev/null || true; xcrun simctl bootstatus $UDID
xcrun simctl install $UDID <path to FeedTheGoose.app>
xcrun simctl io $UDID recordVideo --codec h264 --force /tmp/out/scene.mp4 >/tmp/rec.log 2>&1 &
REC=$!; sleep 2
# drive the scene, then:
kill -INT $REC; wait $REC
xcrun simctl io $UDID screenshot /tmp/out/scene.png
```

- Drive the scenes with XCUITest, in a `DemoTests` class that is not part of `just ios-uitest`.
  Springboard hides the widget gallery's controls from the accessibility tree, so adding a
  widget taps coordinates, as `spikes/swiftui-goose/UITests/AddWidgetTests.swift` does. It
  took the spike four runs.
- Copy the captures to the orb with `mac_download`. `ffmpeg` and `magick` are on the orb, not
  on the Mac.
- Join the scenes with `ffmpeg`, with a title card before each naming the scene. Keep the file
  under 15 MB: scale to 600 pixels wide, H.264, `-crf 24`.
- Scene 6 is captured with `agent-browser` on the orb at 2x.
- **Inspect before reporting.** Watch the whole recording and check every scene against its
  "Shows" column. A scene that did not show what it claims is re-recorded or reported as
  missing, never left in.
